// THE GRENADE MODEL, from RS_Main.
//
// ONE POSE ON EVERY FRAME, and that is RS_Main's finding carried over rather
// than rediscovered: a sprite-frame cycle does nothing to a model, so the
// tumble has to be REAL rotation. RS_VRGrenade.Tick spins roll and pitch by 13
// and 7 degrees a tic once it leaves your hand, and the model follows because
// of the two USEACTOR flags below.
//
// A Skin line, because its absence is silent: the model renderers skip a mesh
// outright when no skin resolves -- no warning, no error, no draw.
Model RS_VRGrenadeThrown
{
	Path "models/grenade"
	Model 0 "nade.md3"
	Skin 0 "nade.png"

	// A SECOND COPY OF THE MESH, WEARING A RED SKIN.
	//
	// This is how the fuse is shown, and it is a skin swap rather than anything
	// cleverer because the clever options do not work here. A MODELDEF
	// Translation is a palette remap and this mesh is skinned with a truecolor
	// PNG, so a translation does nothing at all. RenderStyle Stencil works, but
	// only on the world path: RenderHUDModel passes playermo->RenderStyle
	// (models.cpp:1408) -- the PLAYER's -- so stencilling a psprite-drawn model
	// would tint the whole player instead of the grenade.
	//
	// A second model index with its own skin is immune to all of that. It is the
	// same geometry addressed by a different FrameIndex, so switching to it costs
	// one frame number and works identically on both draw paths.
	Model 1 "nade.md3"
	Skin 1 "nade_red.png"
	Scale 0.3 0.3 0.3
	// PIVOTOFFSET, BECAUSE THE MESH IS NOT CENTRED ON ITS OWN ORIGIN.
	//
	// Measured out of the file at frame 0 and scaled by the 0.3 below: the body
	// spans -8.60 to -3.85 map units vertically about the model origin, and sits
	// 5.85 units off to one side of it. A Doom actor rests with its origin ON the
	// floor, so drawn raw the grenade was 8.6 units underground and a quarter of a
	// metre sideways of where it actually was.
	//
	// PIVOTOFFSET AND NOT OFFSET, and the difference is the whole reason the
	// engine gained the field. Offset is applied AFTER the rotations, so it moves
	// the model without moving the point the model turns about -- it would have
	// put the grenade on the floor and left it ORBITING its old origin every time
	// it tumbled. PivotOffset is subtracted BEFORE them, which is the ordinary
	// v' = R * (v - p): the mesh is moved onto its intended centre of rotation
	// first, then spun about it.
	//
	// So one number fixes both faults at once. It sits on the floor at rest AND
	// spins in place in flight.
	//
	// Z is the mesh's own vertical: raising by 8.597 brings its BASE to the
	// origin, which is where a thing lying on a floor should meet it.
	PivotOffset 5.848 0.0 -8.597

	// FLAGS BEFORE THE FrameIndex LINES. Each FrameIndex pushes a COPY of the
	// in-progress frame carrying whatever flags are set at that moment, so a
	// flag written after the last one parses cleanly and applies to nothing.
	NoInterpolation
	USEACTORPITCH
	USEACTORROLL


	// THE FRAME TABLE, AND THE ORDER OF THESE LINES IS LOAD-BEARING.
	//
	// A FrameIndex line sets the frame for the ONE model index it names and
	// leaves every other index at whatever the previous line left it -- then
	// pushes a COPY of that accumulated state. So writing the plain frames and
	// the red frames as two independent groups does not give you two variants:
	// it gives you entries where BOTH models are set, and both meshes draw, one
	// inside the other. The red one wins because it is drawn second, which is
	// why the grenade came out red permanently rather than flashing.
	//
	// The carry-over is also the fix. A model index parked at -1 is not drawn, so
	// setting the unwanted one to -1 FIRST makes every line after it clean until
	// something changes it back.
	//
	// H and I are scratch: their only job is to carry that -1 into the lines
	// below them. They are never displayed -- nothing sets frame H or I -- and
	// the sprite lookup only validates the four-letter name, not the letter, so
	// they cost two unused table entries and nothing else.

	FrameIndex JGRN H 1 -1    // from here down: the red mesh is off
	FrameIndex JGRN A 0 0     // safe
	FrameIndex JGRN G 0 16    // live -- lever flown

	FrameIndex JGRN I 0 -1    // from here down: the plain mesh is off
	FrameIndex JGRN E 1 0     // safe, red
	FrameIndex JGRN F 1 16    // live, red
	// So every state has a pose that already exists and nothing is faked. Eight
	// sprite letters is all JGRN has, which is exactly enough.
	// animation, which swings the whole grenade up into view. So "safe" on 0 and
	// "pin out" on 10 moves the body twenty units -- the dancing.
	// Moving BOTH poses onto the 2-10 group fixes the dance and moves where the
	// grenade sits, which throws away seating that was found by hand in a
	// The pin coming out is reported by sound and haptics instead. If it needs to

	// and nothing else -- no render style, no colour maths, no per-path special
	// case. E mirrors A and F mirrors G.
}


// THE GRENADE IN YOUR HAND -- one block per controller.
//
// SEATED BY THE RENDERER, NOT BY THE PLAYSIM. FollowMainHand/FollowOffHand take
// the transform straight from GetWeaponTransform at DRAW time, the same wire
// the world hands ride. The alternative -- letting RS_Held carry the actor with
// TryMove -- is Doom movement, and Doom movement COLLIDES: the grenade orbited
// the hand at player-radius plus its own instead of sitting in the palm, which
// is exactly the failure rs_held.zs already documents for barrels.
//
// Two classes because MODELDEF binds per class and a Follow flag names one
// specific controller. The prop is spawned for whichever hand holds it.
//
// SCALE IS IN METRES. Downstream of a Follow flag the engine has already
// applied vr_vunits_per_meter, so mesh space is metres and NOT map units --
// this is the distinction that hid the world hands completely. Body mesh
// measures 15.95 units on its long axis; a 0.09 m grenade is 0.09 / 15.95 =
// 0.005642.

// THE SAME GRENADE, DRAWN THE OTHER WAY.
//
// Two ways to have it in your hand, chosen by rsvg_psprite, because neither is
// simply better:
//
//   PSPRITE (this block)  drawn on the weapon layer, exactly like every gun.
//     Inherits whatever you already tuned for your hands and needs no separate
//     actor. But a psprite is drawn OVER the world -- put your hand behind a
//     wall and the grenade shows through it -- and it is lit by the HUD path
//     rather than by the room it is in.
//
//   WORLD ACTOR (RS_VRGrenadeHeldMain/Off above)  a real thing in the room, so
//     it is occluded by geometry and lit by the sector. Costs a second actor
//     and its own seating.
//
// Nothing in the gestures depends on which: the pin and the throw read palm and
// HMD positions, which are real either way.
//
// SCALE 0.5643, AND THE DIFFERENCE FROM 0.005642 IS EXACTLY 100.
// RenderHUDModel applies a further scale(0.01f) on top of GetWeaponTransform
// (models.cpp:934-937) that the world path does not. So the same mesh at the
// same real size needs a number one hundred times larger here. 15.95 mesh units
// x 0.01 = 0.1595 m at Scale 1.0, and 0.09 / 0.1595 = 0.5643.
